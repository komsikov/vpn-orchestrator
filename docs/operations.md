# Эксплуатация

## Запуск и CLI

```bash
sudo vpn-orchestrator -c /etc/vpn-orchestrator/config.toml
```

| Параметр | Назначение |
| --- | --- |
| `-c`, `--config <PATH>` | Путь к TOML, по умолчанию `/etc/vpn-orchestrator/config.toml`. |
| `--monitor-interval <SECS>` | Интервал логирования пиров серверного интерфейса, по умолчанию 30 секунд. |
| `--skip-server` | Не вызывает `wg-quick`/`awg-quick` для серверного интерфейса. |
| `--log-file <PATH>` | Переопределяет `[logging].file`. |
| `--quiet` | Отключает логирование. |

## Failover и direct fallback

1. Сервис поднимает все включённые upstream-интерфейсы и подготавливает отдельные маршруты для проб.
2. Первый upstream, прошедший health-check, становится активным.
3. После `failover_threshold` неудач активного upstream сервис ищет доступный upstream в порядке конфигурации.
4. При переключении обновляются клиентский маршрут и, если включён `masquerade`, NAT/FORWARD-правила. Если настройка NAT неудачна, сервис пытается восстановить прежний маршрут и правила.
5. Если здоровых VPN нет, сервис остаётся запущенным, пытается восстановиться каждые 10 секунд и настраивает прямой выход через обычный default route из `main`.
6. После восстановления VPN клиентский маршрут и NAT возвращаются на него.

Прямой fallback означает, что маршрутизация настроена без VPN. Он не доказывает доступность внешнего интернета. Если у сервера нет подходящего IPv4 default route или его нельзя применить, клиентская таблица очищается, а событие `direct_fallback_failed` сообщает о недоступности клиентского выхода.

При остановке сервис удаляет свои маршруты и NAT/FORWARD-правила. Он опускает только интерфейсы, которые поднял сам; внешне управляемые интерфейсы остаются поднятыми.

## Логи

По умолчанию логи идут в stdout на уровне `info`. `RUST_LOG` имеет приоритет над `[logging].level`.

```toml
[logging]
enabled = true
file = "/var/log/vpn-orchestrator.log"
level = "info"
max_size_mb = 10
keep_mb = 1
```

`max_size_mb = 0` отключает лимит. При положительном лимите `keep_mb` должен быть меньше него; `keep_mb = 0` очищает файл при ротации. Один файловый writer сохраняет последние полные строки, поэтому нет гонки между rename и записью. Медленный диск может задерживать логирование. Ошибки файла выводятся в stderr как `log_write_failed`, восстановление — `log_write_restored`. Сохранение очереди не гарантируется при `SIGKILL`, аварии диска или питания.

Ключевые события:

- `vpn_unavailable` — не осталось доступного VPN;
- `direct_fallback_enabled` — клиентский маршрут переключён на обычный интерфейс;
- `direct_fallback_failed` — не удалось настроить даже прямой выход;
- `vpn_still_unavailable` — отказ продолжается, запись не чаще раза в минуту;
- `vpn_restored` — VPN восстановлен и прямой выход отключён;
- `https_probe_failed` и `https_probe_restored` — изменение HTTPS-доступности. При `RUST_LOG=debug` запись для каждого недоступного URL содержит причину curl.

## Диагностика

```bash
sudo journalctl -u vpn-orchestrator -f
ip route show table 100
ip rule list
sudo nft list table ip vpn_orchestrator_nat
sudo wg show
ip link show wg0 wg1
```

Внешние firewall-цепочки могут блокировать FORWARD независимо от правил сервиса. При смене исходного VPN-адреса существующим TCP/UDP-сессиям может потребоваться переподключение.
